# shrincs

A Rust reference implementation of [SHRINCS](https://github.com/SHRINCS/shrincs-bip),
the semi-stateful hash-based signature scheme posted to bitcoin-dev on
27 August 2026 as a draft BIP.

> **Not for production.** The draft says so of itself: it has no security
> proof, no test vectors of its own, and is not submitted to the BIPs
> repository. This crate has had no audit. It exists to be read beside the
> specification and to check claims against.

## The scheme in one paragraph

One 48-byte public key carries two signing paths. The **stateful** path signs
with a WOTS+C leaf of an FXMSS tree, from 548 bytes, and needs a counter that
must never repeat. The **stateless** fallback is SLH-DSA under a non-standard
parameter set, a fixed 5,777 bytes, and needs no state at all. Either verifies
against the same key, so losing the counter costs signature size rather than
funds. The two are cross-bound — each path's message digest carries the other
path's root — so neither component can be lifted out and used on its own.

## Usage

```rust
use shrincs::{keygen, sign, verify, Structure};

let seed = [7u8; 48];
let (sk, pk) = keygen(&seed, Structure::balanced(3));   // budget 2^3 = 8

// Stateful. The caller owns the counter; see the warning below.
let sig = sign(b"hello", b"", &sk, Some(0), None).unwrap();
assert_eq!(sig.len(), 580);
assert!(verify(b"hello", &sig, b"", &pk));

// No counter available: the fallback signs instead, and still verifies.
let fallback = sign(b"hello", b"", &sk, None, None).unwrap();
assert_eq!(fallback.len(), 5777);
assert!(verify(b"hello", &fallback, b"", &pk));
```

## The state counter is the sharp edge

Signing twice under one counter value hands anyone who sees both signatures
the ability to forge a third. The draft's rules are MUST-level, and this crate
cannot enforce them for you:

- persist the counter **before** releasing the signature;
- never restore it from a backup, export it, or sign concurrently with it;
- when the counter is uncertain, pass `None` and take the larger signature.

Two things soften this compared with XMSS or LMS. Every key pair carries the
stateless fallback by construction, so lost state costs bytes rather than
funds; and reuse is publicly detectable, since each stateful signature exposes
its leaf position, so a repeat under one key is visible before the second
transaction confirms.

## Tree shapes

| | budget | signature |
|---|---|---|
| `Structure::unbalanced(d)` | `d + 1` | 548 B rising by 16 or 17 per signature |
| `Structure::balanced(d)` | `2^d` | fixed, `530 + 18 + 16·d` bytes |

Shape does not change the cost at a given budget, only the size curve:
unbalanced front-loads the small signatures, balanced flattens them. Exhausting
the budget is not an error — the fallback signs instead.

## Testing

```sh
cargo test
```

`tests/kat.json` was generated by running the reference Python extracted from
the draft itself, so the vectors check this crate against the document rather
than against itself. They cover key generation, every stateful signature of two
tree shapes, and the stateless fallback, byte for byte. Alongside them:

- `verify_parameter_consistency()` re-derives every size the draft states from
  its defining equations, so a mistyped constant fails the suite rather than
  silently producing a scheme that is not SHRINCS;
- the constant-sum property is asserted directly — the verifier walks
  `32 × 15 − 240 = 240` chain steps for every message, which is the whole point
  of WOTS+C over a checksum;
- tampering tests cover message swaps, context swaps, single flipped bits at
  four positions, and verification under the wrong key, on both paths.

## Choosing a hash

The draft specifies SHA-256 and nothing else, deliberately: it is the hash
Bitcoin consensus already has. `Shrincs256`, and the free functions at the crate
root, are that scheme.

The construction itself does not depend on SHA-256, so the primitive sits behind
a trait. A suite supplies a digest, a keyed mode, and how much padding follows
the seed; the nine named functions of the draft are derived from those once.
BLAKE3 is included behind the `blake3` feature as a second instantiation.

```rust
use shrincs::{Shrincs, Shrincs256, hash::Sha256};
type Spec = Shrincs<Sha256>;          // identical to Shrincs256
```

**A scheme instantiated with any suite other than SHA-256 is not SHRINCS.** It
does not interoperate, the draft's security argument does not transfer, and the
known-answer tests do not apply. `tests/suites.rs` asserts the non-interoperability
rather than leaving it to be assumed: same seed and shape give different keys, and
a signature made under one suite fails under the other.

## Against the C++ implementation

[`comparison/`](comparison/) reproduces a same-machine measurement against
`BlockstreamResearch/shrincs-cpp`, which implements an earlier design — `w = 256`
over 16 chains with PORS+FP, where the draft specifies `w = 16` over 32 chains
with FORS. The older design is smaller and slower, the draft's parameters larger
and faster, which is the trade the working group described. The numbers cannot
separate parameter choice from implementation effort, and the directory says so.

## Layout

| Module | Contents |
|---|---|
| `params` | Every constant, derived from its defining equation where there is one |
| `adrs` | The 22-byte address that makes each hash call a distinct function |
| `hash` | The tweakable hash family, all SHA-256 |
| `wots` | WOTS-TW (checksum) and WOTS+C (constant sum) |
| `fxmss` | The variable-shape stateful tree and its shape-agnostic verifier |
| `stateless` | XMSS, the hypertree, FORS, and SLH-DSA over them |

`hash::HashSuite` is the trait; `hash::Sha256` is the specified instantiation.
